# MCL 리플레이 하네스 — 파라미터 변경을 실측으로 가르는 도구

## 왜 필요했나

2026-08-18 실차 백에서 MCL 횡오차가 평균 0.20 m 나왔습니다. 그런데 백만 봐서는
**원인을 못 가릅니다.** 제안분포가 좁아서 못 따라가는 것인지, 출력단(EKF·스무딩)이
입자 추정에서 끌어내는 것인지, 입자 수가 모자란 것인지 — 같은 입력에 파라미터 하나만
바꿔 돌려야 갈립니다.

실차에는 GT가 없으므로 채점도 직접 만들어야 했습니다.

## 구성

| 파일 | 하는 일 |
|---|---|
| `tools/mcl_windows.py` | 백에서 연속 자율주행 구간을 찾아 `--start/--duration` 을 뽑아 줍니다 |
| `tools/mcl_replay.sh` | 그 구간을 노드에 다시 먹이고 결과를 녹화합니다 |
| `tools/mcl_score.py` | GT 없이 횡오차를 채점합니다 |
| `tools/mcl_pose_at.py` | 씨앗 포즈를 백에서 꺼냅니다 (하네스 내부용) |
| `tools/mcl_seed_pose.py` | 그 포즈를 `/initialpose` 로 쏩니다 (하네스 내부용) |

## 쓰는 법

```bash
# 1) 자율주행 구간 찾기
python3 src/monte_carlo_localization/tools/mcl_windows.py rosbag2_2026_08_18-19_41_22

# 2) 기준선
bash src/monte_carlo_localization/tools/mcl_replay.sh \
     rosbag2_2026_08_18-19_41_22 base --start 172.3 --duration 15.5 --warmup 5

# 3) 파라미터 하나만 바꿔서
bash src/monte_carlo_localization/tools/mcl_replay.sh \
     rosbag2_2026_08_18-19_41_22 noekf --start 172.3 --duration 15.5 --warmup 5 \
     use_pose_ekf=false

# 4) 채점
python3 src/monte_carlo_localization/tools/mcl_score.py runs/mcl_replay/base runs/mcl_replay/noekf
```

오버라이드는 `mcl_config.yaml` 에 **이미 있는 키만** 받습니다. 오타가 조용히 무시되면
"바꿨는데 결과가 같다"는 가짜 결론이 나오기 때문입니다.

## 채점이 재는 것과 못 재는 것

`/pf/pose/odom` 으로 스캔을 맵에 얹고, 헤딩 법선 방향으로 얼마나 밀어야 벽에 가장 잘
붙는지를 훑습니다. 그 보정량이 횡 위치오차의 추정치입니다.

**못 재는 것**

- **종방향(s)** — 복도형 트랙이라 스캔이 s 를 구속하지 않습니다. 2차원으로 풀면 해의
  50%가 탐색 경계로 미끄러졌습니다. 그래서 1차원만 풉니다. s 정확도는
  `speed_to_erpm_gain` 이 쥡니다.
- **초기 수렴** — 시작 포즈를 원본 백에서 씨앗으로 주므로, 이 하네스는 "이미 수렴한
  뒤의 추종오차"만 잽니다.
- **절대 정확도** — GT 가 아닙니다. 잔차에 요 오차·맵 오차·라이다 노이즈가 섞입니다.
  최적 보정 후에도 잔차 p50 이 0.10 m 에서 안 내려가는 것이 방법의 바닥값입니다
  (맵 해상도 0.05 m). **변경 전후 비교에만 쓰십시오.**

## 하네스를 짜며 막힌 것 (같은 함정을 다시 밟지 않도록)

1. **거리장을 '점유셀까지의 거리'로 잡으면 안 됩니다.** 이 맵은 트랙 바깥이 통째로
   점유라, 스캔을 그 안으로 밀면 잔차가 0이 되어 최적화가 탐색 경계로 달아납니다.
   '자유/점유 경계면까지의 거리'(|SDF|)를 씁니다.
2. **좀비 노드.** `ros2 launch` 를 죽여도 자식은 삽니다. 살아남은 노드는 **자기 시계가
   멈춘 채** `/pf/pose/odom` 을 계속 내고, 다음 실행의 같은 이름 노드와 충돌합니다.
   실제로 리플레이 결과가 원본보다 3배 나빴는데 전부 좀비가 낸 값이었습니다.
   지금은 시작 전 청소 + 프로세스 그룹째 종료 + `/particle_filter` 중복 검사를 합니다.
3. **종료 순서.** 재생이 끝나면 `/clock` 이 멈추는데 노드는 살아서 얼어붙은 시각으로
   계속 발행합니다. 녹화기를 먼저 기다리면 그 쓰레기가 수백 개 섞입니다. MCL 을
   **먼저** 내리고 녹화기를 나중에 내립니다.
4. **워밍업에 긴 정지 구간을 넣지 마십시오.** 25 s 워밍업(대부분 정지)으로 돌렸더니
   입자 구름이 붕괴해 주행 시작과 함께 헤딩이 88° 틀어졌습니다. 5 s 면 충분합니다.
   (이건 하네스의 결함이 아니라 **MCL 의 실제 성질**로 보입니다 — 별도 확인 필요.)

## 신뢰성 검증

리플레이가 원본을 재현하는지 매번 확인하십시오. 08/18 기준:

```
구간 172.3+15.5   위치차 p50 0.026~0.193 m   헤딩차 p50 0.31~1.60 deg
구간   7.1+ 8.3   위치차 p50 0.072 m         헤딩차 p50 0.83 deg
```

## 결과 (2026-08-18, rosbag2_2026_08_18-19_41_22)

구간 A = `--start 172.3 --duration 15.5`, 구간 B = `--start 7.1 --duration 8.3`.
숫자는 `평균 / p90 / 잔차>0.20 m`.

| 설정 | 구간 A | 구간 B |
|---|---|---|
| 기준선 | 0.135 / 0.320 / 33.0% | 0.274 / 0.610 / 38.7% |
| `motion_dispersion_y=0.05` | 0.152 / 0.350 / 32.0% | — |
| `max_particles=2000` | 0.130 / 0.320 / 28.7% | — |
| `ekf_gate_chi2=0` (게이트 해제) | 0.136 / 0.330 / 32.6% | — |
| `ekf_trans_error_rate=0.10` (실측값) | 0.122 / 0.290 / 29.6% | — |
| `ekf_trans_error_rate=0.25` (실측 p90) | 0.109 / 0.240 / 21.9% | — |
| `ekf_trans_error_rate=1.0` | 0.096 / 0.200 / 14.0% | 0.132 / 0.230 / 10.0% |
| `ekf_trans_error_rate=3.0` | 0.089 / 0.190 / 10.1% | — |
| `=1.0` + `ekf_meas_long_inflation=1.0` | 0.086 / 0.170 / 8.2% | 0.115 / 0.220 / **4.6%** |
| `use_pose_ekf=false` | **0.081** / 0.170 / 5.9% | **0.093** / 0.200 / 8.7% |

`잔차>0.20 m` 열이 실무적으로 가장 중요합니다. `obstacle_detector` 의
`wall_assoc_distance_m` 가 0.20 이라, 이 비율이 그대로 벽 오검출(유령)로 이어집니다.

### 읽는 법

**1. 입자 필터는 문제가 아닙니다.** 입자 수를 4배(500→2000)로 올려도, 횡 제안
노이즈를 5배로 키워도 달라지지 않습니다(후자는 오히려 악화). 오프라인으로 센서모델을
재현해 보면 우도 곡선은 날카롭고(1 nat 폭 중앙값 0.04 m) 최댓값이 발행 포즈에서 평균
0.18 m 떨어져 있습니다 — 정보는 있는데 출력이 거기 없습니다.

**2. 게이트는 무죄입니다.** 아예 꺼도 0.136 vs 0.135 로 무변화입니다.

**3. 휠 오도메트리 오차율이 3배 과소평가돼 있습니다.** 1초 창에서 오도메트리 이동과
MCL 이동을 비교해 실측한 값(3개 백):

```
종방향 오차/이동거리   평균 0.105 ~ 0.128    p90 0.202 ~ 0.325
횡방향 오차/이동거리   평균 0.050 ~ 0.071
횡/종 비             0.47 ~ 0.68
```

현재 `ekf_trans_error_rate: 0.03`, `ekf_lat_error_ratio: 0.3` 입니다. 각각 약 3배·2배
작습니다. **이건 그 자체로 고칠 값입니다.**

**4. 그런데 실측값으로 고쳐도 문제는 안 풀립니다.** `0.03 → 0.10` 은 0.135 → 0.122,
격차의 10%만 메웁니다. 격차가 닫히는 것은 `1.0` 이상 — 물리적으로 "주행거리의 100%가
오차"라는 말이 안 되는 값, 즉 **오도메트리를 사실상 안 믿는 설정**일 때뿐입니다.

칼만 게인으로 보면 분명합니다. 4 m/s·40 Hz 에서 정상상태 `p ≈ √(QR)`, `K = p/(p+R)`:

```
Q(0.03, 현재)   K ≈ 0.026   시상수 0.93 s   →  4 m/s 면 3.7 m 를 달려야 따라잡음
Q(0.10, 실측)   K ≈ 0.077   시상수 0.33 s
Q(1.0)          K ≈ 0.45    시상수 0.06 s   ≒ 통과나 다름없음
```

**5. 그래서 진짜 문제는 EKF 의 전제입니다.** 칼만 필터는 측정 오차가 백색잡음이라
가정하고 평균해서 줄입니다. 그런데 MCL 오차는 백색이 아니라 **천천히 변하는 편향**
입니다(런마다 한쪽으로 7~9 cm 쏠린 것을 실측). 편향을 오도메트리와 평균해 봐야 줄지
않고 **지연만 붙습니다.** Q 를 키워 개선되는 것은 필터가 그만큼 통과기에 가까워지기
때문이지, 융합이 잘 되어서가 아닙니다.

### 6구간으로 넓힌 결과 — 결론이 바뀝니다

구간 두 개(합 24 s)로 낸 "EKF 를 고치면 된다"는 **성급했습니다.** 세 백의 자율주행
구간 여섯 개(합 43 s, 스캔 1,429개) 전부로 넓히면 이렇습니다. 칸은 `평균 / max` [m].

| 구간 | 기준선 | 실측 Q<br/>(0.10/0.55) | Q=1.0<br/>+long=1 | EKF 끄기 |
|---|---|---|---|---|
| 19_41 172.3+15.5 | 0.135/0.760 | 0.134/0.600 | 0.086/0.580 | **0.081**/0.590 |
| 19_41 7.1+8.3 | 0.274/1.200 | 0.182/1.080 | 0.115/0.410 | **0.093**/0.310 |
| 19_47 17.6+4.8 | 0.031/0.100 | **0.018**/0.080 | 0.049/0.100 | 0.122/0.910 |
| 19_47 74.9+4.3 | 0.036/0.140 | 0.041/0.160 | 0.035/0.130 | **0.029**/0.090 |
| 19_51 20.8+5.9 | **0.061**/0.240 | 0.077/0.240 | 0.104/1.200 | 0.080/0.360 |
| 19_51 4.7+4.0 | 0.085/0.100 | 0.082/0.130 | **0.058**/0.110 | 0.113/0.180 |
| **가중 합계** | 0.124 / 21.1% | 0.108 / 19.5% | **0.084 / 4.3%** | 0.088 / 6.6% |

(합계 셋째 열은 `잔차>0.20 m` 비율. 최악 max: 기준선 1.200 / 실측 1.080 / Q=1.0 1.200 / 끄기 0.910)

**어느 설정도 모든 구간에서 이기지 못합니다.** 구간별 승자가 넷 다 다릅니다.

큰 개선은 **기준선 오차가 애초에 컸던 두 구간(A·B)에만** 나타납니다. 나머지 네 구간은
기준선이 이미 좋고(평균 0.031~0.085, 잔차>0.20 이 0~2.7%), 거기서는 바꿔 봐야 무의미
하거나 오히려 나빠집니다 — EKF 를 끈 설정은 19_47 17.6 구간에서 0.031 → 0.122 로
**4배 악화**했고, Q=1.0 은 19_51 20.8 구간에서 1.2 m 스파이크를 냈습니다(기준선엔 없던 것).

물리적으로 실측한 Q(0.10)는 합계로 0.124 → 0.108, **격차의 극히 일부만** 메웁니다.
"Q 가 3배 과소평가돼 있다"는 사실이지만 **그것이 원인은 아닙니다.**

### 지금 말할 수 있는 것 / 없는 것

**말할 수 있는 것 (표본과 무관한 계산)**

현재 설정의 칼만 게인은 4 m/s·40 Hz 에서 `K ≈ 0.026`, 시상수 0.93 s 입니다. MCL 이
"20 cm 옆"이라 해도 한 주기에 5 mm 만 움직입니다. 이건 파라미터에서 바로 나오는
수치라 표본 문제가 아닙니다. 오차가 빠르게 변하는 구간(코너·이탈 직후)에서 이 지연이
그대로 오차로 남습니다.

**말할 수 없는 것**

- 어느 설정이 실차에서 나은지. 43 초로 정할 문제가 아닙니다.
- 효과가 왜 구간에 따라 갈리는지. A·B 가 다른 구간과 무엇이 다른지 아직 모릅니다.

### 권고

**지금은 바꾸지 마십시오.** 자율주행 데이터가 43 초뿐입니다. 내일 주행에서 자율 구간을
길게 확보한 뒤 같은 하네스로 다시 돌리는 것이 순서입니다.

바꾼다면 `ekf_trans_error_rate: 0.03 → 0.10`, `ekf_lat_error_ratio: 0.3 → 0.55` 만이
**측정으로 정당화되는** 변경입니다(실측 오차율). 합계 개선은 작지만 새 실패 모드를
만들지 않았고 최악값도 줄었습니다(1.200 → 1.080).

### 아직 결정하지 않은 것

- 표본이 두 구간(합 24 s)뿐입니다. 다른 백·다른 구간으로 넓혀야 합니다.
- EKF 를 끄면 MCL 글리치 방어가 사라집니다. 그 보험이 실제로 몇 번 값을 했는지
  세어 보지 않았습니다.
- `use_pose_ekf=false` 는 `smoothing_alpha` 경로로 넘어갑니다. 출력이 거칠어지는지
  미확인입니다.
- 요 오차율(`ekf_rot_error_rate`)은 위 실측이 "미터당"이라 파라미터 정의("회전량 대비")와
  단위가 달라 비교하지 않았습니다. 따로 재야 합니다.
