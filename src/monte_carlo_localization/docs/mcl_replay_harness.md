# MCL 리플레이 하네스 — 파라미터 변경을 실측으로 가르는 도구

## 왜 필요했나

2026-08-18 실차 백에서 MCL 횡오차가 평균 0.20 m 나왔습니다. 그런데 백만 봐서는
**원인을 못 가릅니다.** 제안분포가 좁아서 못 따라가는 것인지, 출력단(EKF·스무딩)이
입자 추정에서 끌어내는 것인지, 입자 수가 모자란 것인지 — 같은 입력에 파라미터 하나만
바꿔 돌려야 갈립니다.

실차에는 GT가 없으므로 채점도 직접 만들어야 했습니다.

## 구성

| 파일 | 하는 일 |
|---|---|
| `tools/mcl_windows.py` | 백에서 연속 자율주행 구간을 찾아 `--start/--duration` 을 뽑아 줍니다 |
| `tools/mcl_replay.sh` | 그 구간을 노드에 다시 먹이고 결과를 녹화합니다 |
| `tools/mcl_score.py` | GT 없이 횡오차를 채점합니다 |
| `tools/mcl_pose_at.py` | 씨앗 포즈를 백에서 꺼냅니다 (하네스 내부용) |
| `tools/mcl_seed_pose.py` | 그 포즈를 `/initialpose` 로 쏩니다 (하네스 내부용) |

## 쓰는 법

```bash
# 1) 자율주행 구간 찾기
python3 src/monte_carlo_localization/tools/mcl_windows.py rosbag2_2026_08_18-19_41_22

# 2) 기준선
bash src/monte_carlo_localization/tools/mcl_replay.sh \
     rosbag2_2026_08_18-19_41_22 base --start 172.3 --duration 15.5 --warmup 5

# 3) 파라미터 하나만 바꿔서
bash src/monte_carlo_localization/tools/mcl_replay.sh \
     rosbag2_2026_08_18-19_41_22 noekf --start 172.3 --duration 15.5 --warmup 5 \
     use_pose_ekf=false

# 4) 채점
python3 src/monte_carlo_localization/tools/mcl_score.py runs/mcl_replay/base runs/mcl_replay/noekf
```

오버라이드는 `mcl_config.yaml` 에 **이미 있는 키만** 받습니다. 오타가 조용히 무시되면
"바꿨는데 결과가 같다"는 가짜 결론이 나오기 때문입니다.

## 채점이 재는 것과 못 재는 것

`/pf/pose/odom` 으로 스캔을 맵에 얹고, 헤딩 법선 방향으로 얼마나 밀어야 벽에 가장 잘
붙는지를 훑습니다. 그 보정량이 횡 위치오차의 추정치입니다.

**못 재는 것**

- **종방향(s)** — 복도형 트랙이라 스캔이 s 를 구속하지 않습니다. 2차원으로 풀면 해의
  50%가 탐색 경계로 미끄러졌습니다. 그래서 1차원만 풉니다. s 정확도는
  `speed_to_erpm_gain` 이 쥡니다.
- **초기 수렴** — 시작 포즈를 원본 백에서 씨앗으로 주므로, 이 하네스는 "이미 수렴한
  뒤의 추종오차"만 잽니다.
- **절대 정확도** — GT 가 아닙니다. 잔차에 요 오차·맵 오차·라이다 노이즈가 섞입니다.
  최적 보정 후에도 잔차 p50 이 0.10 m 에서 안 내려가는 것이 방법의 바닥값입니다
  (맵 해상도 0.05 m). **변경 전후 비교에만 쓰십시오.**

## 하네스를 짜며 막힌 것 (같은 함정을 다시 밟지 않도록)

1. **거리장을 '점유셀까지의 거리'로 잡으면 안 됩니다.** 이 맵은 트랙 바깥이 통째로
   점유라, 스캔을 그 안으로 밀면 잔차가 0이 되어 최적화가 탐색 경계로 달아납니다.
   '자유/점유 경계면까지의 거리'(|SDF|)를 씁니다.
2. **좀비 노드.** `ros2 launch` 를 죽여도 자식은 삽니다. 살아남은 노드는 **자기 시계가
   멈춘 채** `/pf/pose/odom` 을 계속 내고, 다음 실행의 같은 이름 노드와 충돌합니다.
   실제로 리플레이 결과가 원본보다 3배 나빴는데 전부 좀비가 낸 값이었습니다.
   지금은 시작 전 청소 + 프로세스 그룹째 종료 + `/particle_filter` 중복 검사를 합니다.
3. **종료 순서.** 재생이 끝나면 `/clock` 이 멈추는데 노드는 살아서 얼어붙은 시각으로
   계속 발행합니다. 녹화기를 먼저 기다리면 그 쓰레기가 수백 개 섞입니다. MCL 을
   **먼저** 내리고 녹화기를 나중에 내립니다.
4. **워밍업에 긴 정지 구간을 넣지 마십시오.** 25 s 워밍업(대부분 정지)으로 돌렸더니
   입자 구름이 붕괴해 주행 시작과 함께 헤딩이 88° 틀어졌습니다. 5 s 면 충분합니다.
   (이건 하네스의 결함이 아니라 **MCL 의 실제 성질**로 보입니다 — 별도 확인 필요.)

## 신뢰성 검증

리플레이가 원본을 재현하는지 매번 확인하십시오. 08/18 기준:

```
구간 172.3+15.5   위치차 p50 0.026~0.193 m   헤딩차 p50 0.31~1.60 deg
구간   7.1+ 8.3   위치차 p50 0.072 m         헤딩차 p50 0.83 deg
```

## 첫 결과 (2026-08-18, rosbag2_2026_08_18-19_41_22)

| 설정 | 평균 | p50 | p90 | max | 잔차>0.20 m |
|---|---|---|---|---|---|
| **구간 A** (172.3+15.5) | | | | | |
| 기준선 | 0.135 | 0.090 | 0.320 | 0.760 | 33.0% |
| `use_pose_ekf=false` | **0.081** | 0.060 | 0.170 | 0.590 | **5.9%** |
| `motion_dispersion_y=0.05` | 0.152 | 0.110 | 0.350 | 0.900 | 32.0% |
| `max_particles=2000` | 0.130 | 0.080 | 0.320 | 0.770 | 28.7% |
| **구간 B** (7.1+8.3) | | | | | |
| 기준선 | 0.274 | 0.170 | 0.610 | 1.200 | 38.7% |
| `use_pose_ekf=false` | **0.093** | 0.060 | 0.200 | 0.310 | **8.7%** |

두 구간 모두 **EKF 를 끄면 오차가 절반 이하**가 됩니다. 입자 수도, 횡 제안 노이즈도
효과가 없었습니다 — 즉 입자 필터는 답을 알고 있었고 **출력단이 그걸 망치고 있었습니다.**

`잔차>0.20 m` 열이 특히 중요합니다. `obstacle_detector` 의 `wall_assoc_distance_m` 가
0.20 이라, 이 비율이 그대로 벽 오검출(유령)로 이어집니다. 33% → 6% 는 유령이 거의
사라진다는 뜻입니다.

⚠️ 아직 **끄자고 결론 내릴 단계는 아닙니다.** EKF 는 스캔이 나쁠 때의 보험으로 들어온
장치입니다. 확인해야 할 것:
- 자율 구간 표본이 두 개(합 24 s)뿐입니다. 다른 백·다른 구간으로 넓혀야 합니다.
- EKF 를 끄면 출력이 거칠어질 수 있습니다(`smoothing_alpha` 경로로 넘어감).
- EKF 의 어느 부분이 문제인지 아직 모릅니다 — R 산정인지, 게이트인지, 프로세스 노이즈인지.
  끄는 것보다 그 안을 고치는 쪽이 옳을 수 있습니다.
