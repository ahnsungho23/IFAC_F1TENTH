## 1. 지연 비교 — Kinematic-ICP vs MCL (핵심 질문)

"제어기가 포즈를 실제로 사용하는 시점에 그 포즈가 얼마나 오래된 것인가"를 두 백에 동일하게 측정
(`/drive` 수신 시각 − 직전 `/pf/pose/odom`의 header.stamp):

| 지표 | Kinematic-ICP (08-18) | MCL (08-10) |
|---|---|---|
| 포즈 나이 중앙값 | **17.0 ms** | 42.3 ms |
| 포즈 나이 p95 | **32.3 ms** | 62.6 ms |
| 포즈 나이 p95 (v>4 m/s) | **27.5 ms** | 62.5 ms |
| 포즈 나이 최대 (v>4 m/s) | **43.6 ms** | 142.5 ms |
| 포즈 발행 레이트 | 39.9 Hz (스캔마다) | ~20 Hz (갭 多) |
| 주행 중 포즈 점프 | **0건** | 4건 (0.42~2.23 m, 최대 2.23 m @ 3.3 m/s 주행 중) |
| 포즈 publish 지연 (수신−스탬프) | 중앙 8.3 ms | 스탬프 자체가 보상됨(lidar+처리시간) |

참고: Kinematic-ICP는 포즈를 **스캔 종료 시각**으로 스탬핑하고(`localization_node.cpp`의
`out_stamp`), MCL은 `last_lidar_time_ + 처리시간`으로 보상 스탬핑한다(`particle_filter.cpp:1579`).
스탬핑 관례는 다르지만, 위 "포즈 나이" 지표는 이 관례 차이를 포함한 종단간 실측값이며
KICP가 모든 분위에서 더 신선하다.

결론: **지연은 벽 스침의 원인이 아니다.** 오히려 이번 구성에서 지연이 절반 이하로 줄었다.

### 음수 클리어런스의 해석

클리어런스 = 라인 파일의 `d_left`/`d_right` − frenet `d` 이므로, 음수는 "라인 파일이 선언한
트랙 경계 밖"이라는 뜻이다. 차량이 물리적으로 벽 너머에 있을 수는 없으므로 다음 중 하나:
(a) 라인의 트랙 경계가 실제 벽보다 안쪽(보수적)으로 잡혀 있음 — 경계 데이터 불일치,
(b) 해당 코너에서 위치추정이 수십 cm 편향됨 — 단, 정지 중에도 ICP가 맵에 잘 정렬된 채
유지됐으므로 맵 자체와 실제 트랙(당일 코스 레이아웃)의 차이일 가능성이 있다.
백만으로는 (a)/(b) 구분 불가 — 라인 재생성 시 경계 산출 로직과 당일 맵(map_0818_track.kissmap,
08-18 15:43 제작)의 정합성을 함께 점검할 것.

## 6. 추가 분석 — "코너에서 진동하듯 벌어지는" 양상 (2026-08-18 추가)

실주행 관찰(코너에서 항상 진동하듯 크게 벌어짐)을 백에서 정량 검증:

| 지표 (자율, v>3 m/s) | KICP 08-18 | MCL 08-10 |
|---|---|---|
| 코너(|κ|>0.15) d 방향반전 | **53회/min** | 4회/min |
| 코너 d 고주파 std | 0.052 m | 0.117 m |
| 조향각 방향반전 | **422회/min** (진폭 std 1.4 mrad로 작음) | 15회/min |
| 포즈 yaw 잔차(휠 ω·dt 대비) std | 0.639° | 3.83° |
| 포즈 횡방향 스텝 std | 7.1 mm | 111 mm |
| `/pf/pose/odom` twist.vx 노이즈(휠 대비 std) | **0.285 m/s** (편향 −0.12 m/s) | 0.086 m/s |
| twist.vy / wz | 노이즈 채워짐 (std 0.34 / 1.0) | 0 / 0 (미발행) |

포즈(x, y, yaw) 자체는 KICP가 MCL보다 훨씬 깨끗하다. 다른 곳에 있었다:

**근본 원인 — twist 채널.** MCL은 `/pf/pose/odom`의 twist에 **휠 오도메트리 속도**를 실어주는데
(`particle_filter.cpp:1676`), Kinematic-ICP 노드는 ICP 포즈 델타로 속도를 추정해 실었다
(vx 노이즈 std 0.285 m/s, vy/wz도 노이즈). `control_map_node`는 이 토픽의 `twist.linear.x`를
`current_speed_`로 사용하며(`control_map_node.cpp:403`), 이 값이 L1 전방거리
(`l1_offset + v·l1_speed_gain`), 속도 PI 오차, 곡률 사전감속 거리(`v²/2a`)를 모두 움직인다.
속도 추정이 40 Hz로 ±0.3 m/s씩 떨리면 전방거리·스로틀·감속 시점이 함께 디더링되고,
코너에서는 이것이 "진동하듯 라인을 오가며 벌어지는" 거동으로 보인다. MCL 시절에는 이 입력이
깨끗했으므로 같은 제어기에서 안 보이던 현상이다. (obstacle_detector의 `twist.angular.z`,
opp_planning의 `hypot(vx, vy)` 소비처도 같은 노이즈를 먹고 있었다.)

**조치 (edge_test, `src/kinematic_localization/src/localization_node.cpp`)**:
`/pf/pose/odom`의 twist를 휠 오도메트리 값으로 전달하도록 수정(MCL과 동일 관례:
`linear.x`/`angular.z`만, `linear.y`=0). ICP 델타 속도 추정 코드는 삭제.
백 재생 스모크 테스트로 확인: 주행 구간에서 twist.vx=4.86 m/s(휠 5.66 부근, 감속 중),
vy=0.0, wz=−0.18 — 포즈 출력 경로는 미변경.
