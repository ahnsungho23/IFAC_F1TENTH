# Reference Oracle v2 specification

Status: **FROZEN BEFORE SEEN-DATA RECOMPUTATION**  
Machine-readable authority: `oracle_v2_spec.json`

## Claim boundary

Reference Oracle v2 is a deterministic offline exhaustive search over an explicitly finite, event-specific request set. It guarantees that every unique request in that declared set is submitted to the frozen C++ P3 constructor and, if construction succeeds, to the exact frozen validator once. It is **not** a proof over the continuous P3 parameter space and is not a real-time planner.

No new path family is introduced. Every request reconstructs the existing five-knot, four-segment, C2 quintic-Hermite Frenet P3 using the frozen harness. The directly searched tuple is

`(clearance gate, side, d_target, d_mid, entry_scale, exit_scale)`.

`s_probe` and `d_probe` are not independent spline degrees of freedom once `d_mid` is given. They remain generator lineage. Exact production root/probe-derived `d_target` and `d_mid` values are nevertheless inserted as anchors.

## Finite domain

For each event, gate in `{STRICT, RELAXED}`, and side in `{RIGHT, LEFT}`:

1. Ask the frozen harness for the exact valid side-specific target interval.
2. Build `d_target` from a 0.01 m grid with origin 0, exact interval endpoints, every in-range same-side production target, every in-range complete frozen factor-pool target, and a clipped `±0.04 m` local 0.01 m lattice around production targets.
3. Build `d_mid` from the closed interval `[-1.5, 1.5] m` on the same 0.01 m grid, exact endpoints, all same-side production and complete factor-pool midpoints, and a clipped `±0.04 m` local lattice around production midpoints.
4. Use every unique exact `(entry_scale, exit_scale)` pair generated by production for that evaluator input. No new transition factor is added.
5. Submit the full Cartesian product of target, midpoint, and transition-pair sets.
6. Union every exact STRICT production request and every exact STRICT request tuple in the complete frozen factor pool before any selector top-K. This includes bit-exact boundary production values and out-of-interval factor targets: they are submitted so the same C++ construction/validation path, constructed-count, digest, and verdict can be audited. This union is selector-outcome-independent.

Float anchors are retained by exact Python-float equality, not epsilon coalescing. This matters for digest-level reconstruction: VUE036 contained two numerically near-equal midpoint anchors whose few-ULP difference changed the reconstructed path digest.

## Enumeration and completeness

Ordering is deterministic: STRICT before RELAXED, RIGHT before LEFT, then ascending target, midpoint, entry scale, and exit scale. Exact request tuples are deduplicated before submission. Path digests are computed only after construction/validation for accounting and parity; they never prune the request space.

There is no top-N refinement, violation-score pruning, valid-result early stop, or outcome-conditioned anchor generation. After forming the Cartesian set and exact factor-request union, the unique requests are sorted by the declared ordering. Chunking is transport only and cannot change the domain or order.

## Construction guards

The frozen adapter preserves the production construction path and exposes its outcomes instead of silently dropping requests:

- Event input must contain a finite ego snapshot and nonempty reference; request scalars must parse as finite numbers.
- The P3 planning context and requested side domain must exist for the selected STRICT/RELAXED clearance gate.
- `stationsFor()` computes the same five knot stations from the side domain and requested transition scales.
- A non-positive quintic-Hermite segment is caught at the same construction boundary as production and emitted as an explicit unconstructed row (`point_count=0`, no validator execution).
- Constructed splines with fewer than the frozen `minimum_path_points` are emitted but do not invoke the hard validator.
- All remaining constructed paths undergo the unchanged geometry recomputation, velocity shaping, diagnostic measurement, and exact hard validation. Validator failures are results, not oracle pruning criteria.

The exact production/factor request union may contain a target just outside the reported interval by exact comparison. Such a tuple is included only for reconstruction parity and follows the same C++ construction/validation path; it does not enlarge the uniform Cartesian target grid.
